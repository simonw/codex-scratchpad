# How Codex Orchestrates a Coding Session

The open-source Codex CLI is structured around an explicit event/state machine rather than a single prompt. When a session starts, `Codex::spawn` wires up submission and event channels, creates a `Session`, and launches an async `submission_loop` that keeps running until shutdown.【F:codex/codex-rs/core/src/codex.rs†L180-L227】【F:codex/codex-rs/core/src/codex.rs†L1103-L1485】 A `Session` owns the durable pieces of state (conversation history, approved commands, token/rate-limit data) alongside service handles such as the rollout recorder and MCP/tool managers.【F:codex/codex-rs/core/src/codex.rs†L262-L272】【F:codex/codex-rs/core/src/state/session.rs†L1-L80】【F:codex/codex-rs/core/src/state/service.rs†L1-L18】 Per-turn concerns live in `ActiveTurn`/`TurnState`, which track the running task, pending approvals, and queued user input that arrives while the model is busy.【F:codex/codex-rs/core/src/state/turn.rs†L1-L115】 The combination of these structs is the in-memory state machine that front-ends like the TUI query and manipulate.

## Submission loop and task management

All user-facing actions (`/interrupt`, `/review`, `/model`, etc.) become `Op` submissions. The `submission_loop` matches on each op to mutate the turn context or dispatch work: it can override the model/cwd, enqueue extra user input into the active turn, spawn a new task when no turn is running, start review/compact tasks, or shut everything down cleanly.【F:codex/codex-rs/core/src/codex.rs†L1103-L1485】 When a new task is needed, `Session::spawn_task` first aborts any existing task, records the new `RunningTask` in `ActiveTurn`, and ensures only one task runs at a time. Completion and abort events are emitted in one place so the UI can render consistent lifecycle transitions.【F:codex/codex-rs/core/src/tasks/mod.rs†L59-L163】 Because user input can arrive mid-turn, `inject_input` either buffers it on the current turn or hands it back to start a fresh turn, keeping the state machine responsive.【F:codex/codex-rs/core/src/codex.rs†L1015-L1034】【F:codex/codex-rs/core/src/codex.rs†L1212-L1309】 Review requests spin up a dedicated review task that swaps in review-specific prompts, models, and isolated history before emitting mode-change events, illustrating how the loop branches into specialized substates.【F:codex/codex-rs/core/src/codex.rs†L1487-L1571】 

## Turn execution loop

`run_task` is the inner driver. It records the user’s message, prepares turn-specific history (isolated for review threads, shared otherwise), and then repeatedly calls `run_turn` until the model stops requesting tool calls. Each iteration processes pending buffered input, dispatches tool results, watches token limits, and emits TaskStarted/TurnDiff/UserNotification events to external observers.【F:codex/codex-rs/core/src/codex.rs†L1574-L1871】 If the turn ends normally the last assistant message is preserved; if it errors or the user interrupts, abort events flow back out so the UI can recover.【F:codex/codex-rs/core/src/codex.rs†L1801-L1850】

`run_turn` encapsulates the API interaction: it builds the prompt (including tool availability and optional JSON schemas), retries streaming failures with exponential backoff, and surfaces retry diagnostics to the user. Every streamed item is processed immediately so secondary state machines (token usage, diff tracking, MCP client list) stay in sync.【F:codex/codex-rs/core/src/codex.rs†L1900-L1962】 Inside `try_run_turn`, Codex normalizes missing tool call completions, persists turn context snapshots, and drives the streaming response. Each `ResponseItem` triggers handler logic that either queues another `ResponseInputItem` (for tool outputs) or emits UI events (for assistant/reasoning/web-search messages).【F:codex/codex-rs/core/src/codex.rs†L1980-L2166】 The core handler supports built-in tools, MCP tools, local shell commands, and custom tool outputs, logging telemetry and packaging the result back to the model with success metadata.【F:codex/codex-rs/core/src/codex.rs†L2177-L2299】 This loop continues until the model produces a pure assistant message, at which point Codex records the message, sends user notifications, and exits the task state.【F:codex/codex-rs/core/src/codex.rs†L1748-L1835】 

## Putting it together

The architecture is therefore a queue-driven state machine layered over explicit session/turn structs. Submissions mutate top-level session state, spawn or replace turn tasks, and the task loop alternates between streaming model output and executing tools until a stable assistant answer emerges. The separation between durable session data, per-turn mutable state, and async task orchestration is what lets Codex “course correct,” retry, or branch into review/compact flows instead of relying on a single prompt. That end-to-end lifecycle is fully visible in the open-source code above, providing the detailed architecture overview the original question was looking for.
